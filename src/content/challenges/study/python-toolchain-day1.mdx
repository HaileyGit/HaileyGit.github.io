JS 위주로 일해온 개발자입니다. AI 공부를 시작하면서 Python 환경을 처음으로 제대로 세팅했는데, npm은 손에 익었어도 Python 생태계는 거의 처음이라 하루 종일 부딪혔어요. 그날 알게 된 것들을 정리해서 공유드립니다. (개념 위주로, 특정 강의 내용은 뺐어요.)

---

## 1. uv, Python에도 드디어 "npm"이 생겼다

JS는 처음부터 깔끔했어요. `npm install` 하면 `node_modules`에 프로젝트별로 깔리고, `package.json`이랑 `package-lock.json`으로 버전이 고정됩니다. 그게 끝이에요.

Python은 이게 없었어요. 도구가 여기저기 흩어져 있었습니다.

- `pip`은 패키지 설치는 되는데 기본이 전역 설치라 프로젝트끼리 버전이 충돌해요.
- `venv`는 격리 환경을 손으로 만들고 활성화해야 하고요.
- lock 파일은 기본으로 안 줍니다. `requirements.txt`를 수동으로 챙겨야 했어요.
- 파이썬 버전 관리는 또 `pyenv`라는 별도 도구가 따로 있었습니다.

uv는 이걸 하나로 합쳐놨어요. 게다가 Rust로 짜여서 `pip`보다 열 배에서 백 배까지 빠르다고 합니다.

명령어 매핑부터 외우니까 금방 적응됐어요.

```
uv init           = npm init        (프로젝트 생성)
uv add 패키지      = npm install 패키지
uv sync           = npm install     (lock/toml 보고 전부 설치)
uv run main.py    = npx / node main.js (환경 안에서 실행)
pyproject.toml    = package.json
uv.lock           = package-lock.json
.venv/            = node_modules/
```

재밌었던 건, 패키지 하나(`requests`)를 추가했는데 5개가 깔렸다는 거예요. 나머지 4개는 전이 의존성, 그러니까 그 패키지가 내부적으로 가져다 쓰는 것들이고, 그 정확한 버전이 `uv.lock`에 박힙니다. `package-lock.json`이랑 똑같은 얘기였어요.

## 2. Rust가 왜 자꾸 나오지?

`uv`가 "Rust로 짜여서 빠르다"는 말이 계속 나와서 한 번 짚고 넘어갔어요.

Rust는 미리 기계어로 컴파일해서 네이티브 바이너리로 돕니다. Python이나 JS는 실행할 때마다 해석(interpret)하는데, Rust는 그 과정이 없으니 빠르고 가벼워요. 가비지 컬렉터도 없는데 메모리는 안전하다고 하고요. 컴파일러가 그걸 막아주는 식이라고 합니다.

저한테 남은 결론은 하나였어요. "Rust로 짰다는 건 빠르다는 뜻." `pip`은 Python으로 짜여서 느린데, `uv`는 컴파일된 Rust 바이너리라 설치가 순식간이었습니다.

요즘은 느린 기존 도구를 Rust로 다시 짜는 게 흐름이라고 해요. `ruff`(린터), `uv`, JS 쪽의 `swc`나 `biome` 같은 것들이 다 그런 경우입니다.

---

## 3. 가상환경(.venv), JS의 node_modules를 Python은 손으로 만들어야 했다

Python은 기본적으로 패키지를 시스템 전역에 깝니다. 그러면 프로젝트 A는 `X==1.0`이 필요하고 B는 `X==2.0`이 필요할 때 충돌이 나요. JS는 `node_modules`가 폴더 안에 박히니까 이 문제가 애초에 없었습니다.

`.venv`가 그 격리된 "버블"이에요. 프로젝트 폴더 안에 자기 패키지를 따로 깔아서 전역을 더럽히지 않습니다.

그리고 알게 된 건, conda든 venv든 uv든 다 같은 목적(격리된 환경)이고 만든 도구만 다르다는 거였어요. 데이터나 학교 쪽은 conda를 많이 쓰고, 제 경우 AI 강의는 uv를 씁니다. conda의 `base`도 결국 "환경 하나"일 뿐이었어요.

## 4. 오늘 제일 크게 와닿은 것: 격리는 공짜가 아니다

처음엔 "uv가 프로젝트마다 환경을 따로 만들어주니까 항상 그렇게 해야 하나" 싶었어요. 아니었습니다.

프로젝트마다 격리하는 이유는 딱 하나, 의존성 충돌을 막으려는 거예요.

| 상황 | 선택 |
|---|---|
| 무겁고 서로 충돌하는 deps (프로젝트마다 다름) | 격리 (환경 따로) |
| 가벼운 같은 deps, 충돌 없음 | 환경 하나 공유 |

작은 스크립트(기껏 `requests` 하나 쓰는) 하나하나를 과제마다 새 환경에 격리하면, 막을 충돌도 없는데 똑같은 패키지가 든 폴더만 잔뜩 복제됩니다. 그냥 낭비예요.

> 격리는 공짜가 아니다. 충돌이 있을 때만 격리해라.

이게 그날 제일 본전 뽑은 한 줄이었어요. 도구가 "할 수 있다"고 해서 반사적으로 다 갖다 쓰지는 말자, 하고요.

## 5. Python이 강한 자리는 따로 있다

언어마다 주력 영역이 갈린다는 걸 정리해두니 그림이 잡혔어요.

| 영역 | 주력 |
|---|---|
| 백엔드 | JS(Node), Python, Java, Go... |
| AI/ML/데이터 | Python 압도적 |

그럼 Python으로 낸 결과를 브라우저에는 어떻게 띄우지? 길이 두 개 있었습니다.

하나는 FastAPI나 Flask, Django로 Python이 JSON API나 HTML을 서빙하고, 그걸 JS 클라이언트가 받아서 그리는 방식이에요. 제가 늘 하던 정석 구조죠. 다른 하나는 Streamlit이나 Gradio처럼 Python 스크립트를 그대로 웹 UI로 바꿔주는 방식인데, UI 코드를 한 줄도 안 짜도 됩니다. AI 데모에서는 이게 표준이라고 해요.

## 6. Jupyter 노트북, 셀 단위로 바로 결과가 보인다

터미널 출력만 보다가 답답했는데, Jupyter를 쓰니 결과가 바로바로 눈에 들어왔어요.

`.ipynb` 파일은 코드를 셀(cell) 단위로 조각조각 실행합니다. 그 셀을 실제로 돌리는 엔진이 커널(kernel)인데, `ipykernel` 패키지가 그 역할을 하고 환경마다 따로 깔아줘야 했어요. 그리고 셀 마지막 줄에 변수명만 적으면 `print` 없이도 값이 출력돼서, dict 구조를 까볼 때 제일 편했습니다.

API 응답(JSON)을 셀에서 바로 까보면서 "이 값을 어떻게 꺼내지"를 실험할 수 있어서, 한 번에 다 짜는 것보다 훨씬 손에 잡혔어요.

---

## 7. JS 습관 하나 깨기: dict는 점이 아니라 대괄호

API 응답에서 값을 꺼내다가 바로 틀렸어요.

```python
data.title       # ❌ JS 습관 → AttributeError
data["title"]    # ✅ Python dict는 키로 꺼낸다
```

JS에서 `obj.title`이 손에 박혀 있어서 무의식적으로 점을 찍었는데, Python dict는 `["키"]`로 접근합니다. `.json()`이 돌려주는 게 dict라서 여기서 자주 걸릴 것 같아요.

## 마무리

하루 해보고 느낀 건, 새 언어인데도 기존 언어랑 비교하니까 이해가 쉬웠다는 거예요. 새 도구 이름에 겁먹기보다 "이건 내가 아는 무엇무엇이랑 같은 역할"로 매핑하니까 속도가 붙었습니다.

다만 하나 헷갈렸던 건, 화면으로 결과가 나오는 데 익숙하다가 터미널만 계속 보고 있으니 좀 낯설었어요. 눈에 보이는 UI 없이 텍스트 출력만 따라가는 감각이 아직 안 붙었습니다. (그래서 Jupyter가 더 반가웠던 것 같기도 해요.)

반복해서 나온 교훈은, 도구 이름보다 개념이 먼저라는 거예요. API는 바뀌어도 격리나 의존성, 환경 같은 개념은 안 바뀌니까요.
